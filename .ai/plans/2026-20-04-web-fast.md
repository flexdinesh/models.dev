## Title

React web v2 prototype in `packages/web-fast`

## Brief Summary

Build a parallel static React app in `packages/web-fast` that reads the existing provider/model source data via `packages/core`, emits a compact homepage payload at build time, and keeps current UX parity while avoiding the current giant SSR table and DOM-based search.

## Key Implementation Changes

- Create new isolated workspace at `packages/web-fast`
- Use `Vite + React` for a static build to `dist/`
- Add a build step that flattens generated provider/model data into a compact table-specific payload
- Keep current public API shape untouched by not modifying existing `packages/web` or `packages/function`
- Implement client-side search/sort/query-param behavior in React
- Render the table with virtualization so only visible rows mount in the DOM
- Preserve current homepage UX in v1: columns, sorting, search, copy model ID, help modal

## Tests Or Verification

- Run `bun validate`
- Run `cd packages/web-fast && bun run build`
- Verify v2 output files are generated and smaller than the current SSR-heavy homepage approach
- Verify search, sort, URL params, copy model ID, and help modal behavior in the built app
- Verify no existing workspace files are modified outside approved scope if avoidable

## Decisions Made By User

- Build new app in `packages/web-fast`
- Do not touch existing workspaces for rollout
- Use `Vite + React`
- Keep same table UX for v1
- Keep `/api.json` as-is
- Use memory index first
- Drop full-table SSR
- Treat v2 as parallel prototype for now

## Tradeoffs And Risks Discussed

- Main bottleneck is current large HTML/DOM, not just raw dataset size
- React alone would not help if full-table SSR stayed
- Memory search is simpler than IndexedDB and should be enough for ~4k rows once DOM work is removed
- Virtualized table adds some implementation complexity around sticky headers and row measurement
- Keeping v2 isolated avoids deploy risk but means later cutover is separate work
